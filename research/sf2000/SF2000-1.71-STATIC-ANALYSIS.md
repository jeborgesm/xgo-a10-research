# SF2000 Stock Firmware 1.71 — Preservation and Static Analysis

**Specimen:** `DATAFROG-SF2000-1.71-OS-Files.zip`  
**Analysis date:** 2026-09-23  
**Status:** Offline static analysis; hardware validation pending replacement microSD media.  
**Evidence discipline:** Direct observations and interpretations are separated below. No specimen files were modified.

## Purpose

This archive is the clean stock SF2000 1.71 file-level reference specimen for XGO A10 family archaeology. It provides a fixed upstream comparison point for the XGO card-resident firmware, resource store, frontend configuration, emulator integration, save-state paths, and later Multicore work.

The archive is an **OS-files package, not a sector image**. It establishes file-level content but does not preserve FAT allocation/order, partition geometry, volume metadata, deleted entries, or bootloader state outside the files.

## Package inventory

Extraction produced **173 regular files totaling 86,646,932 bytes**.

Top-level payload:
- `bios/` — main executable firmware and emulator BIOS archives.
- `Resources/` — frontend resources, fonts, configuration and opaque/obfuscated data containers.

There are **no stock ROM-library directories** in this package.

### BIOS directory

- `bios/bisrv.asd` — 12,624,628 bytes; main card-resident SF2000 application/firmware payload.
- `bios/gba_bios.bin` — GBA BIOS payload.
- `bios/neogeo.zip` and `bios/neogeo1.zip` — Neo Geo BIOS archives.
- `bios/pgm.zip` — IGS PGM BIOS archive.

## Canonical bisrv.asd fingerprint

Measured directly from the supplied archive:

- Size: **12,624,628 bytes**
- CRC32: **33B9FB14**
- SHA-256: **fb772d3af075f60cf26a0b923d428bfa35907fff168f55aaa328fd89e21cbb2b**

The CRC32 matches the independently documented SF2000 v1.71 fingerprint identified during source verification. `file(1)` identifies the binary only as generic data; it is not a conventional ELF/PE container.

## Direct firmware-string evidence

Static ASCII extraction from `bios/bisrv.asd` exposes, among others:

- `h1512_gpio_pinmux_sel`
- `%s/Resources/Archive.sys`
- `%s/Resources/%s`
- `%s/Resources/KeyMapInfo.kmp`
- `%s/Resources/Foldername.ini`
- `SF2000`
- `%s/save/%s.sa%d`
- `%s/%s/save/%s.sa%d`
- `save_state: %s`
- `Open_state: %s`
- `save_state:%s`
- `load_state:%s`
- `load_state complete`
- `ROM_MEM_BUFFER = 0x%X, ROM_MEM_BUFFER_SIZE = %dM`
- `fceumm_region`
- `catsfc_VideoMode`
- numerous FBA/Neo Geo option and BIOS strings.

**Observed:** The monolithic binary directly knows resource paths, save-state naming, the SF2000 identity, an H1512 GPIO symbol, and emulator-specific configuration names.

**Interpretation:** Multiple emulator implementations appear integrated into the application rather than being discovered solely as external executables. Strings alone do not establish function boundaries or runtime ownership.

**Observed:** `SF2000` is the first literal. The file names FC, SFC, MD, GB, GBC, GBA and ARCADE and associates them with repeated `FF8000`; `FFFFFF` is also present.

**Interpretation:** The six-digit hexadecimal values strongly resemble RGB colors and the final tuples appear to be UI/layout parameters. Keep this as inference until code/runtime correlation.

## Resources/KeyMapInfo.kmp

- Size: **288 bytes**
- Binary, not text.
- Begins with small little-endian-looking integer fields.
- Contains repeated blocks and small values including 8, 9, 10 and 11.

Its name and structure make an input mapping table plausible, but the field semantics are not established. Do not promote this to a decoded key map without behavioral/code correlation.

## Resource-store structure

`Resources/` contains 167 files. Many names/extensions resemble Windows system files (`.dll`, `.cpl`, `.sys`, `.nec`, etc.), but contents do not behave like ordinary Windows binaries.

Repeated binary prefixes occur across unrelated-looking extensions:
- 35 files begin with eight zero bytes.
- 19 begin `FF FF FF 00 FF FF FF 00`.
- 8 begin `CB 01 CB 01 CB 01 CB 01`.
- 5 begin `A2 10 A2 10 A2 10 A2 10`.

**Finding:** filename extension is not a reliable type identifier in this store.

**Interpretation:** Windows-like names are best treated as opaque resource identifiers/camouflage until individual formats are decoded.

Fonts include `Arial_cn.ttf`, `Arial_en.ttf`, `Arial_jp.ttf`, `Arial_kr.ttf`, `yahei_Arial.ttf`, and `Tahoma.ttf`, directly supporting multilingual frontend rendering.

## Arcade BIOS evidence

`neogeo.zip` and `neogeo1.zip` contain broad Neo Geo BIOS sets including Universe BIOS variants, AES/MVS BIOS files, `sfix`, `sm1`, and region/system BIOS variants.

`pgm.zip` contains six PGM components: `bios.u42`, `ddp3_bios.u37`, `pgm_m01s.rom`, `pgm_p01s.u20`, `pgm_p02s.u20`, and `pgm_t01s.rom`.

Together with Neo Geo/FBA strings in `bisrv.asd`, this directly shows that arcade support includes both BIOS dependencies and emulator configuration logic.

## Save-state contract evidence

The firmware contains:
- `%s/save/%s.sa%d`
- `%s/%s/save/%s.sa%d`

plus save/load diagnostics.

This establishes a stock `.saN` naming convention and more than one path-construction form. Exact per-platform routing and placeholder semantics require code-level tracing/runtime observation. This is a useful pristine upstream target for comparison with the XGO CLASSIC save-state work.

## Critical limitation: this ZIP is not boot media

The archive does **not** preserve:
- FAT32 boot sector or MBR/partition table,
- FAT cluster allocation,
- physical directory-entry ordering,
- volume serial/label,
- deleted directory entries,
- card-controller behavior,
- bootloader state outside these files.

Therefore failure to boot after copying these files to a new card would not invalidate the archive. It would indicate an additional media-level contract, formatting detail, missing directory skeleton, or card compatibility issue.

This matters especially because of SF2000-family FAT/`bios` sensitivity and the XGO post-Test100 `bisrv.asd` boot-integrity investigation.

## Preservation rules

1. Preserve the downloaded ZIP byte-for-byte as source specimen.
2. Never edit the canonical extraction in place.
3. Generate experiments from copies.
4. Verify `bisrv.asd` against the fingerprints above before experiments.
5. After the first successful replacement-card boot, create a **sector-for-sector image before modifications**.
6. Record FAT type, allocation-unit size, partition start/size, volume label/serial, formatter and card make/model.
7. Record hashes and hardware result for every later firmware experiment.

## Hardware-validation plan

When replacement 32 GB media arrives:

1. Establish controlled FAT32 media.
2. Copy the clean stock filesystem manually, preserving names/case and avoiding convenience-management tools.
3. Do not add Multicore/themes yet.
4. Test stock boot.
5. On success, power down and image the complete card immediately.
6. Hash and document that image and its FAT/partition metadata.
7. Use the second card for Multicore/comparative archaeology.

If the manually constructed card does not boot, investigate media-level requirements before changing `bisrv.asd`.

## Hardware tests SB01 / SB02 and vanilla-image comparison — 2026-09-25

### Hardware observations

- **SB01:** Fresh 32 GB card, stock 1.71 OS-files package copied manually -> **BLACK SCREEN**.
- **SB02:** Same card with one additional empty `/bios/temp1.txt` entry -> **BLACK SCREEN**.

These results show that adding an entry after the copied files does not reproduce the bootable directory state.

### Vanilla v1.71 disk-image geometry

Direct inspection of `Y_SF2000_TF_V1.71_20231013-VANILLA.img` establishes:

- Disk image size: **16,011,755,520 bytes**
- DOS/MBR partition table; signature `55 AA`
- FAT32 LBA partition type: **0x0C**
- Partition start: **LBA 8192** = 4 MiB
- Partition sectors: **30,525,440**
- FAT32 OEM field: `MSDOS5.0`
- Bytes/sector: **512**
- Sectors/cluster: **64** = 32 KiB clusters
- Reserved sectors: **740**
- FATs: **2**
- FAT size: **3,726 sectors each**
- Root cluster: **2**
- FSInfo sector: **1**
- Backup boot sector: **6**
- Volume label: `NO NAME`
- FAT32 data region begins at absolute offset **0x00800000 (8 MiB)**.

The root directory places `BIOS` at cluster **90326**. Other root entries include ARCADE, FC, GB, GBA, GBC, MD, ROMS, SFC and RESOURCES.

### Critical /bios directory finding

The bootable vanilla image's raw `/bios` directory is not equivalent to a clean five-file directory. Its 32-byte directory entries are:

- offset 0x000: `.`
- offset 0x020: `..`
- offset 0x040: `GBA_BIOS.BIN`
- offset 0x060: `NEOGEO.ZIP`
- offset 0x080: `NEOGEO1.ZIP`
- offset 0x0A0: `PGM.ZIP`
- offsets **0x0C0 through 0x1C0:** **nine deleted `BISRV   ASD` directory entries**
- offset **0x1E0:** live `BISRV.ASD`, size 12,624,628 bytes, starting at cluster **7**.

The live firmware's FAT chain begins `7 -> 8 -> 9 -> 10 -> ...`, demonstrating contiguous low-cluster placement at the start of the data area.

This explains why SB02 was not a valid recreation of the vanilla boot-media state: adding `temp1.txt` appended a new directory entry but did **not** move `BISRV.ASD` to the vanilla image's later directory slot or reproduce the deleted-entry history/low-cluster firmware placement.

### Evidence interpretation

**Directly proven from the image:** geometry above; raw directory-entry sequence; nine deleted BISRV entries; live BISRV at directory offset 0x1E0; live BISRV starting cluster 7; initial contiguous FAT chain.

**Hardware-proven:** SB01 and SB02 both black-screen on the test SF2000.

**Not yet proven:** which of directory-entry position/history, cluster placement/contiguity, bootloader scan behavior, or another image-layout property is individually necessary. Do not collapse these correlated differences into a single causal claim until controlled hardware tests isolate them.

### Next controlled test

**SB03:** Write the vanilla `.img` byte-for-byte to the second 32 GB card without resizing or filesystem repair, then test boot. This is a raw-media reproduction test, not a file-copy test. If SB03 boots, preserve/image/hash that card before any modification and use it as the first hardware-proven SF2000 v1.71 boot baseline.


## SB03 hardware pass — 2026-09-25

**Test:** `Y_SF2000_TF_V1.71_20231013-VANILLA.img` written as a complete disk image to replacement 32 GB microSD, without reconstructing the filesystem by file copy.

**Result: PASS — SF2000 boots.**

### Hardware observations

- The stock frontend reaches the menu normally.
- The menu music is audibly the same as the music used by the tested XGO A10 frontend.
- The SF2000 frontend is visually more colorful than the XGO frontend.
- The SF2000 menu presents game shortcuts/links before entering the corresponding game list.
- In this ROM-less vanilla preservation image those game links do not launch games, as expected because game payloads were intentionally removed.

### What SB03 proves

On this physical SF2000 and replacement media, the preserved v1.71 full-disk image is bootable while the manually reconstructed filesystem from the v1.71 OS-files ZIP (SB01) is not. Therefore file-content equivalence alone is insufficient to reproduce the known-good boot state.

SB03 also substantially reduces the likelihood that the replacement Micro Center card itself or the console hardware is responsible for SB01/SB02. The remaining investigation should focus on media/filesystem-layout differences and the stock bootloader's expectations.

Do **not** yet attribute causality specifically to the nine deleted BISRV directory entries, live BISRV directory offset, cluster-7 placement, contiguity, partition geometry, or another individual property. Those are correlated differences requiring controlled isolation.

### New lineage observation

The identical menu music is a new **hardware-observed frontend asset/lineage clue** linking the stock SF2000 presentation to the tested XGO A10. This is stronger than a generic stylistic resemblance because the same audible asset is present on both physical systems. The exact resource file and whether its bytes are identical remain to be established by resource comparison.

The richer SF2000 menu and its pre-list game shortcuts are also useful comparative frontend evidence: the related firmware family can expose navigation/presentation behavior not surfaced by the XGO's stock skin/configuration.

### Baseline designation

SB03 is the first **hardware-proven SF2000 v1.71 boot-media baseline** in this investigation.

Preserve the vanilla image unchanged. Before modifying the bootable card for Multicore or other experiments, retain a reproducible raw-image baseline and record all later deltas against SB03.


## XGO ↔ SF2000 resource comparison — 2026-09-25

A direct byte-level comparison was performed between the preserved XGO analysis filesystem (`XGoAnalisis.zip`) and the canonical SF2000 v1.71 OS-files package.

### Inventory overlap

- XGO specimen: 113 regular files
- SF2000 v1.71 specimen: 173 regular files
- Same pathname in both: **99**
- Same pathname and byte-identical content: **25**
- Of the 25 exact matches, **21 are under `Resources/`** and four are arcade/console BIOS payloads.

This establishes substantial shared resource payload, not merely similar filenames or visual style.

### Menu music: byte-identical — lineage evidence upgraded

Hardware observation during SB03 reported that the SF2000 menu music sounded the same as the XGO menu music. Community SF2000 documentation identifies `Resources/pagefile.sys` as the main-menu background music, raw signed 16-bit little-endian mono PCM.

Direct comparison now proves:

- XGO `Resources/pagefile.sys`: 3,119,630 bytes
- SF2000 v1.71 `Resources/pagefile.sys`: 3,119,630 bytes
- SHA-256 for both: **366ab6f79d9f85689a379154401dd4148e70210cd89a1352d227728810c526ac**
- Result: **BYTE-IDENTICAL**

Therefore the user's hardware auditory observation is confirmed at file level: XGO and SF2000 ship the exact same main-menu music payload.

### Main-menu shortcut architecture

SF2000 community documentation identifies `Resources/xfgle.hgp` as a plain-text definition of the ROM shortcuts shown on each system's main-menu page. This independently explains the SB03 hardware observation that shortcut presentation remains visible in the ROM-less vanilla image: shortcut configuration is a separate frontend resource and is not simply generated from the current presence of ROM payloads.

The XGO/SF2000 comparison should therefore treat shortcut presentation, ROM-list catalogs, and ROM payload presence as separate layers.


### SB04 hardware result — 2026-09-25

**Test:** Starting from the failed manually reconstructed v1.71 card used for SB01/SB02, retain `/bios/temp1.txt` and add a second zero-byte file, `/bios/temp2.txt`. No other intentional change.

**Result: FAIL — BLACK SCREEN.**

Therefore neither one nor two appended temporary directory entries is sufficient to make this manually reconstructed filesystem boot on the test hardware. This further weakens any simplistic interpretation that visible `/bios` file count alone determines bootability.

Do not modify the hardware-proven SB03 image card. The failed reconstruction remains the experimental card.

The next investigation should compare the actual raw FAT directory-entry sequence and allocation state of the failed reconstruction against SB03 before requesting further hardware changes. In particular, visible file count must not be treated as synonymous with FAT directory-entry count or bootloader-visible file-object state.
