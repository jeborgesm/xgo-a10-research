# SF2000 Stock Firmware 1.71 — Preservation and Static Analysis

**Specimen:** `DATAFROG-SF2000-1.71-OS-Files.zip`  
**Analysis date:** 2026-09-23  
**Status:** Offline static analysis; hardware validation pending replacement microSD media.  
**Evidence discipline:** Direct observations and interpretations are separated below. No specimen files were modified.

## Purpose

This archive is the clean stock SF2000 1.71 file-level reference specimen for XGO A10 family archaeology. It provides a fixed upstream comparison point for the XGO card-resident firmware, resource store, frontend configuration, emulator integration, save-state paths, and later Multicore work.

The archive is an **OS-files package, not a sector image**. It establishes file-level content but does not preserve FAT allocation/order, partition geometry, volume metadata, deleted entries, or bootloader state outside the files.

## Package inventory

Extraction produced **173 regular files totaling 86,646,932 bytes**.

Top-level payload:
- `bios/` — main executable firmware and emulator BIOS archives.
- `Resources/` — frontend resources, fonts, configuration and opaque/obfuscated data containers.

There are **no stock ROM-library directories** in this package.

### BIOS directory

- `bios/bisrv.asd` — 12,624,628 bytes; main card-resident SF2000 application/firmware payload.
- `bios/gba_bios.bin` — GBA BIOS payload.
- `bios/neogeo.zip` and `bios/neogeo1.zip` — Neo Geo BIOS archives.
- `bios/pgm.zip` — IGS PGM BIOS archive.

## Canonical bisrv.asd fingerprint

Measured directly from the supplied archive:

- Size: **12,624,628 bytes**
- CRC32: **33B9FB14**
- SHA-256: **fb772d3af075f60cf26a0b923d428bfa35907fff168f55aaa328fd89e21cbb2b**

The CRC32 matches the independently documented SF2000 v1.71 fingerprint identified during source verification. `file(1)` identifies the binary only as generic data; it is not a conventional ELF/PE container.

## Direct firmware-string evidence

Static ASCII extraction from `bios/bisrv.asd` exposes, among others:

- `h1512_gpio_pinmux_sel`
- `%s/Resources/Archive.sys`
- `%s/Resources/%s`
- `%s/Resources/KeyMapInfo.kmp`
- `%s/Resources/Foldername.ini`
- `SF2000`
- `%s/save/%s.sa%d`
- `%s/%s/save/%s.sa%d`
- `save_state: %s`
- `Open_state: %s`
- `save_state:%s`
- `load_state:%s`
- `load_state complete`
- `ROM_MEM_BUFFER = 0x%X, ROM_MEM_BUFFER_SIZE = %dM`
- `fceumm_region`
- `catsfc_VideoMode`
- numerous FBA/Neo Geo option and BIOS strings.

**Observed:** The monolithic binary directly knows resource paths, save-state naming, the SF2000 identity, an H1512 GPIO symbol, and emulator-specific configuration names.

**Interpretation:** Multiple emulator implementations appear integrated into the application rather than being discovered solely as external executables. Strings alone do not establish function boundaries or runtime ownership.

The complete 173-byte CRLF text is:

```text
FF8000 GB
FF8000 GBC
FF8000 GBA

```

**Observed:** `SF2000` is the first literal. The file names FC, SFC, MD, GB, GBC, GBA and ARCADE and associates them with repeated `FF8000`; `FFFFFF` is also present.

**Interpretation:** The six-digit hexadecimal values strongly resemble RGB colors and the final tuples appear to be UI/layout parameters. Keep this as inference until code/runtime correlation.

## Resources/KeyMapInfo.kmp

- Size: **288 bytes**
- Binary, not text.
- Begins with small little-endian-looking integer fields.
- Contains repeated blocks and small values including 8, 9, 10 and 11.

Its name and structure make an input mapping table plausible, but the field semantics are not established. Do not promote this to a decoded key map without behavioral/code correlation.

## Resource-store structure

`Resources/` contains 167 files. Many names/extensions resemble Windows system files (`.dll`, `.cpl`, `.sys`, `.nec`, etc.), but contents do not behave like ordinary Windows binaries.

Repeated binary prefixes occur across unrelated-looking extensions:
- 35 files begin with eight zero bytes.
- 19 begin `FF FF FF 00 FF FF FF 00`.
- 8 begin `CB 01 CB 01 CB 01 CB 01`.
- 5 begin `A2 10 A2 10 A2 10 A2 10`.

**Finding:** filename extension is not a reliable type identifier in this store.

**Interpretation:** Windows-like names are best treated as opaque resource identifiers/camouflage until individual formats are decoded.

Fonts include `Arial_cn.ttf`, `Arial_en.ttf`, `Arial_jp.ttf`, `Arial_kr.ttf`, `yahei_Arial.ttf`, and `Tahoma.ttf`, directly supporting multilingual frontend rendering.

## Arcade BIOS evidence

`neogeo.zip` and `neogeo1.zip` contain broad Neo Geo BIOS sets including Universe BIOS variants, AES/MVS BIOS files, `sfix`, `sm1`, and region/system BIOS variants.

`pgm.zip` contains six PGM components: `bios.u42`, `ddp3_bios.u37`, `pgm_m01s.rom`, `pgm_p01s.u20`, `pgm_p02s.u20`, and `pgm_t01s.rom`.

Together with Neo Geo/FBA strings in `bisrv.asd`, this directly shows that arcade support includes both BIOS dependencies and emulator configuration logic.

## Save-state contract evidence

The firmware contains:
- `%s/save/%s.sa%d`
- `%s/%s/save/%s.sa%d`

plus save/load diagnostics.

This establishes a stock `.saN` naming convention and more than one path-construction form. Exact per-platform routing and placeholder semantics require code-level tracing/runtime observation. This is a useful pristine upstream target for comparison with the XGO CLASSIC save-state work.

## Critical limitation: this ZIP is not boot media

The archive does **not** preserve:
- FAT32 boot sector or MBR/partition table,
- FAT cluster allocation,
- physical directory-entry ordering,
- volume serial/label,
- deleted directory entries,
- card-controller behavior,
- bootloader state outside these files.

Therefore failure to boot after copying these files to a new card would not invalidate the archive. It would indicate an additional media-level contract, formatting detail, missing directory skeleton, or card compatibility issue.

This matters especially because of SF2000-family FAT/`bios` sensitivity and the XGO post-Test100 `bisrv.asd` boot-integrity investigation.

## Preservation rules

1. Preserve the downloaded ZIP byte-for-byte as source specimen.
2. Never edit the canonical extraction in place.
3. Generate experiments from copies.
4. Verify `bisrv.asd` against the fingerprints above before experiments.
5. After the first successful replacement-card boot, create a **sector-for-sector image before modifications**.
6. Record FAT type, allocation-unit size, partition start/size, volume label/serial, formatter and card make/model.
7. Record hashes and hardware result for every later firmware experiment.

## Hardware-validation plan

When replacement 32 GB media arrives:

1. Establish controlled FAT32 media.
2. Copy the clean stock filesystem manually, preserving names/case and avoiding convenience-management tools.
3. Do not add Multicore/themes yet.
4. Test stock boot.
5. On success, power down and image the complete card immediately.
6. Hash and document that image and its FAT/partition metadata.
7. Use the second card for Multicore/comparative archaeology.

If the manually constructed card does not boot, investigate media-level requirements before changing `bisrv.asd`.
