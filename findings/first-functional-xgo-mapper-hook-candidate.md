# First functional XGO mapper hook

## Status

**HARDWARE CONFIRMED.**

This was the first functional bridge between the XGO's hardware-proven hidden `gpapi.bvs` pause page and the stock per-game keymap machinery. It deliberately performed one fixed mutation rather than implementing a full editor.

Hardware testing proved the complete live-write side. A separate stock writer/loader filename mismatch initially prevented automatic reload; manually correcting the filename then proved the stock loader as well.

## Minimal page-4 hook

The pause action dispatcher at runtime `0x80355180` handles stock menu states 0..3. The probe changes the final state-3 comparison into a branch-likely:

```asm
# stock
8035519c  bne   v1,t7,0x80354df4
803551a0  lhu   a0,-30364(gp)

# probe
8035519c  bnel  v1,t7,0x80355808
803551a0  sw    zero,0x1908(s2)
```

Raw words:

```text
0x0035519c  0x146fff15 -> 0x546f019a
0x003551a0  0x97848964 -> 0xae401908
```

For state 3, `bnel` is not taken and its delay slot is annulled, preserving the stock state-3 path. For hidden state 4, the branch is taken, the delay-slot mutation executes, and control reaches the existing keymap-writer/resume call site at `0x80355808`.

## Fixed mutation

At pause-function entry:

```text
s2 = 0x8109f65c
active keymap = 0x810a0f58
```

For ordinary systems the P1 physical record order is:

```text
X, Y, L, A, B, R
```

Physical A is record 3 at `0x810a0f64`, exactly `0x1908` bytes above `s2`. Therefore:

```asm
sw zero,0x1908(s2)
```

sets the physical-A record to `0x00000000`, whose low 16-bit logical selector is libretro `B`.

The deliberate result is:

```text
physical A -> logical B
```

## Hardware result

On an SFC/SNES game the probe hardware-confirmed all of the following:

- hidden page 4 is reachable and renders `gpapi.bvs`;
- confirm on page 4 executes the injected mutation;
- physical A immediately behaves as logical B in the running game;
- the stock writer detects the induced P1/P2 mismatch;
- the stock writer synchronizes the corresponding P2 record;
- a 48-byte `.kmp` is written to the SD card;
- the captured file contains the modified A->B mapping in both player halves.

The first relaunch appeared to lose the mapping, but inspection showed the writer had created:

```text
Battletoads In Battlemaniacs.kmp
```

while the stock loader looked for:

```text
Battletoads In Battlemaniacs.zsf.kmp
```

After manually copying/renaming the same hardware-generated file to the loader's expected name, relaunch restored A->B automatically. Thus the mapper hook and the stock loader/writer pipeline are both hardware proven; the only defect was the stock writer using the wrong game-name buffer.

## Persistence repair

The writer/loader mismatch has an exact one-instruction repair at runtime/ASD `0x80354054 / 0x00354054`:

```asm
# stock writer: extensionless display name
addiu a3,a3,-992       # 0x8109fc20

# corrected writer: full ROM filename, matching loader
addiu a3,a3,-792       # 0x8109fce8
```

Raw:

```text
0x24e7fc20 -> 0x24e7fce8
```

The combined candidate is generated by:

```text
tools/patch_mapper_probe_persistent.py
```

## Architectural consequence

The low-level mapper architecture is no longer speculative. Hardware has demonstrated:

```text
gpapi.bvs page
  -> page-4 action hook
  -> live 48-byte map
  -> P1/P2 synchronization
  -> set_keymap()
  -> per-ROM .kmp write
  -> .kmp reload on next launch
  -> restored gameplay mapping
```

The next engineering problem is therefore the actual editor/controller UI: replace the fixed A->B write with a six-position selector, logical-target selection, turbo state, and on-screen feedback using the GB300 behavior already recovered.
