# XGO stock game-list format and SF2000 lineage

Status: **XGO FILE-FORMAT STRUCTURE CONFIRMED FROM CAPTURED SD IMAGE; MENU BEHAVIOR STILL NEEDS HARDWARE TEST**

## Why this matters

The XGO SD-card image contains the same deliberately-obscured resource-list architecture seen in the SF2000 family. This gives us a practical path to adding games to the stock XGO system lists while preserving the stock frontend.

The important correction to the initial hypothesis is that the built-in system lists are **not simply directory enumerations**. The captured XGO card contains physical ROM-wrapper files that are absent from the corresponding English resource list. Therefore the stock list has an explicit catalog/index layer.

The first entries match real files in the corresponding stock directories, e.g. `rdbui.tax` begins with `Contra 1.zfc`, `Contra 2.zfc`, etc.

## Exact binary list format

The XGO list files use a simple deterministic binary structure:

```text
uint32_le count
uint32_le offsets[count]
char string_blob[]
```

Where:

- `count` is the number of list entries;
- each offset is relative to the beginning of `string_blob`;
- strings are NUL-terminated;
- the first offset is normally zero;
- `string_blob` begins at `4 + count * 4`.

Example: `rdbui.tax`

```text
count = 0x000002e8 = 744
string_blob offset = 4 + 744*4 = 0x0ba4
first offsets = 0, 13, 26, 39, 52, ...
```

At `0x0ba4`:

```text
Contra 1.zfc\0
Contra 2.zfc\0
Contra 3.zfc\0
Contra 7.zfc\0
Contra Force 4.zfc\0
...
```

This format was independently recovered from the XGO files rather than assumed from SF2000 documentation.

## Per-system translated/search lists are position-coupled

For the six primary console systems, XGO contains three synchronized lists with exactly the same entry count:

| System | Filename / English | Chinese | Pinyin/search |
|---|---|---|---|
| FC | `rdbui.tax` | `fhcfg.nec` | `nethn.bvs` |
| SFC | `urefs.tax` | `adsnt.nec` | `xvb6c.bvs` |
| MD | `scksp.tax` | `setxa.nec` | `wmiui.bvs` |
| GB | `vdsdc.tax` | `umboa.nec` | `qdvd6.bvs` |
| GBC | `pnpui.tax` | `wjere.nec` | `mgdel.bvs` |
| GBA | `vfnet.tax` | `htuiw.nec` | `sppnp.bvs` |

Every triple has an identical `count` field on the captured XGO card. This strongly indicates entries are linked **by index**, not filename lookup.

The same relationship exists for at least four arcade groups:

```text
mswb7.tax (26)  <-> msdtc.nec (26) <-> mfpmp.bvs (26)
rmapi.tax (117) <-> pcadm.nec (117) <-> ntdll.bvs (117)
kjbyr.tax (28)  <-> djoin.nec (28)  <-> ke89a.bvs (28)
subst.tax (6)   <-> aepic.nec (6)   <-> sensc.bvs (6)
```

The XGO `Foldername.ini` contains five consecutive `ARCADE` main-menu definitions. The exact mapping of those five visible sections to the four confirmed resource-list triples plus any fifth special/shortcut behavior remains to be traced.

## Strong evidence that built-in lists are catalog-driven

Comparing the XGO English resource catalogs with the actual captured filesystem is particularly revealing.

Every filename listed in the primary catalogs exists on disk, but multiple physical game files are **not listed** in the catalog:

```text
FC:  757 physical .zfc files, 744 listed, 13 physical files unlisted
SFC: 1065 physical .zsf files, 929 listed, 136 physical files unlisted
MD:  833 physical .zmd files, 788 listed, 45 physical files unlisted
GB:  967 physical .zgb files, 885 listed, 82 physical files unlisted
GBC: 973 physical .zgb files, 958 listed, 15 physical files unlisted
GBA: 656 physical .zgb files, 626 listed, ~30 physical files unlisted
```

Examples of physical-but-unlisted FC files include:

```text
Bomber Man 2.zfc
Booby Kids.zfc
Commando.zfc
First Defender.zfc
Hokuto No Ken.zfc
Star Soldier.zfc
Top Gun 1.zfc
```

This is powerful evidence against the idea that the built-in NES/SNES/etc. pages are generated by blindly enumerating their directories. If they were, the catalog would be unnecessary and those extra physical files should naturally appear.

The immediate hardware test should therefore be to determine whether one known physical-but-unlisted game is absent from the stock visible list. If so, adding that same filename to the correct three resource lists gives us a controlled no-new-ROM experiment for proving stock-list injection.

## Very useful control case: `/ROMS`

The captured card also contains a `ROMS` directory with ordinary unwrapped ROMs such as `.nes`, `.smc`, `.sfc`, `.gb`, etc. This is distinct from the built-in catalog-backed system pages.

That means the stock frontend appears to support two content models:

```text
built-in system pages
    -> explicit resource catalogs
    -> thumbnail-wrapped .zxx files

ROMS / user content
    -> ordinary ROM files
    -> runtime-generated/user list behavior
```

This distinction is useful because it means "add a playable ROM" and "add a polished built-in-list entry" are separate tasks. The former may already require only copying a supported ROM into `/ROMS`; the latter requires rebuilding the corresponding resource lists and optionally generating a `.zxx` thumbnail wrapper.

## `.zxx` wrapper lineage

SF2000 community research describes `.zfc`, `.zsf`, `.zmd`, and `.zgb` as thumbnail-plus-ROM wrappers, with a 144x208 RGB565 image followed by a ZIP/WQW-style payload. The XGO resource configuration independently reports a `144 208` dimension pair and uses the same wrapper extensions, making this lineage highly plausible for XGO.

Do not yet treat every SF2000 `.zxx` byte-level detail as XGO authority. We should verify the XGO `Resources/Test.zsf` boundary and then compare a generated candidate on hardware.

## SF2000 lineage comparison

Public SF2000 research independently identifies the same filename-list resource names and says they are used for the built-in system menus. It also reports a list-rebuilding tool (`frogtool`) and documents the same system mapping.

This is excellent lineage evidence, but the XGO conclusions above do not depend on it: the counts, offset-table layout, synchronized triples, and physical-vs-listed mismatch were all verified directly from the XGO capture.

A particularly important divergence exists in key mapping behavior: later SF2000 firmware reportedly removed per-game `.kmp` support, while the XGO firmware still contains `%s/save/%s.kmp` and our machine-code analysis reaches a working `set_keymap` implementation. This suggests XGO did not simply inherit the latest stock SF2000 firmware wholesale; it appears to retain/recombine older behavior.

## Next controlled tests

1. **Catalog visibility control:** pick a physical-but-unlisted `.zfc` known to be on the XGO card and confirm it is absent from the visible FC menu.
2. **List-only injection:** append that existing filename to `rdbui.tax` plus aligned placeholder/English values in `fhcfg.nec` and `nethn.bvs`; do not touch the ROM file itself.
3. Boot and confirm the game appears and launches.
4. Once proven, build an XGO list rebuilder that preserves ordering and updates all three synchronized resources transactionally.
5. Independently validate XGO `.zxx` packaging so arbitrary new ROMs can receive stock-style thumbnails.

This path can make adding a game to the stock XGO frontend a deterministic tooling operation instead of a firmware patch.
