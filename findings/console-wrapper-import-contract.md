# XGO console wrapper import contract

Date: 2026-09-06
Branch: `research-game-list-scanning`

Status: **thumbnail boundary and item-0 payload semantics confirmed from XGO; ordinary-ZIP acceptance still requires XGO hardware proof**

## XGO-native launcher proof

The preserved XGO launcher `run_game` is at `0x80360b88`.

The normal browser has two call sites into it. Immediately before each call the preview/header length argument is computed as:

```text
thumbnail_width * thumbnail_height * 2
```

using the configured frontend thumbnail dimensions.

For the shipped XGO configuration:

```text
144 * 208 * 2 = 59904 = 0xEA00
```

`run_game` forwards that value to `unwqw_init(path, preview_size, 2)`.

After package initialization, the console packaged-content path invokes:

```text
unwqw_decompress(handle, 0, destination_buffer, 0, 3)
```

The second argument is explicitly zero.

### Consequence

**CONFIRMED:** XGO decompresses archive item 0 from a console `.zxx` wrapper.

The inner archive filename is therefore not used to choose the emulator or identify the game. The outer filename/extension selects the frontend/emulator family; the first archive entry supplies the ROM bytes.

This removes the OEM legacy-filename scrambling algorithm from the minimum importer requirements.

## Thumbnail contract

`Resources/Test.zsf` independently proves the wrapper geometry:

```text
0x0000..0xE9FF   59,904 bytes
                 144x208 little-endian RGB565

0xEA00..EOF      archive payload
```

Decoding the first 59,904 bytes as little-endian RGB565 reproduces the expected SUPER FAMICOM controller-test artwork correctly.

Therefore a new cover can be generated by resizing/placing artwork at 144x208 and writing each RGB565 pixel little-endian.

## Archive payload

The OEM `Test.zsf` payload uses the WQW signature substitutions:

```text
WQW 03 -> ZIP local-file record
WQW 02 -> ZIP central-directory record
WQW 01 -> ZIP end-of-central-directory record
```

Replacing those three markers with standard PK ZIP signatures yields a valid Deflate ZIP whose first entry decompresses to the exact 131,072-byte controller-test ROM.

## Family tooling evidence

Frogtool's wrapper creator does:

```text
RGB565 144x208 thumbnail
+
raw contents of a .zip/.bkp file
```

without converting ordinary ZIP signatures to WQW.

This is strong family evidence that the underlying OpenZipU/UnzipItem implementation accepts ordinary ZIP behind the thumbnail as well as OEM WQW.

However, **ordinary-ZIP acceptance on this exact XGO build is not yet hardware-confirmed**.

## Import architecture now implied

For FC/SFC/MD/GB/GBC/GBA the minimum polished import pipeline can be:

```text
raw ROM
  -> create single-entry Deflate ZIP

cover image
  -> 144x208 little-endian RGB565

wrapper
  -> RGB565 bytes + ZIP bytes
  -> system-specific outer extension (.zfc/.zsf/.zmd/.zgb)

catalog
  -> stable-append exact outer filename to slot 0
  -> append basename fallback to slots 1 and 2
```

No pre-created save state, `.kmp`, or battery save is required for the basic import path.

## Arcade is different

Do not generalize this console wrapper format to curated Arcade `.zfb` files.

XGO arcade `.zfb` entries are lightweight thumbnail/reference records:

```text
59,904-byte RGB565 thumbnail
4 zero bytes
real ZIP basename
NUL trailer
```

and the actual arcade ROM ZIP lives under `ARCADE/bin/`.

Console and Arcade importers therefore require separate packaging policies.

## Best next proof

The cleanest package-generation hardware test can use the controller-test ROM already embedded in the user's own XGO `Resources/Test.zsf`:

1. extract its known-good item-0 ROM;
2. create a fresh ordinary single-entry ZIP with a simple ASCII inner filename;
3. prepend the known-good 144x208 thumbnail;
4. place the result as a new `.zsf` under `SFC/`;
5. stable-append one synchronized SFC catalog entry;
6. launch it from the normal SFC list.

If that passes, ordinary ZIP wrapper generation is proven on XGO and the future on-device importer no longer needs a WQW writer.
