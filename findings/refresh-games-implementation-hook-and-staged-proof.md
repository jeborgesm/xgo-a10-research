## Natural explicit trigger already exists

The stock User Menu is frontend state 14 and has exactly three selectable rows:

```text
0 User Games
1 Language
2 TV System
```

The confirm-action dispatcher for those rows is at:

```text
0x80359e94
```

It loads the selected User Menu row and dispatches:

```text
selection 0 -> stock User Games path
selection 1 -> language path
selection 2 -> TV-system path
```

The exact row-0 branch is:

```text
0x80359e94  load current User Menu row
0x80359e98  if row == 0 -> 0x80357468
```

Therefore Refresh Games does not need:

- a new screen;
- a fourth menu row;
- an unproven Start/Select raw-event identity;
- a hidden button chord;
- repurposing the volume button.

The lowest-risk integration is:

```text
User Menu
  -> confirm "User Games"
  -> Refresh Games routine
  -> return to exact stock destination 0x80357468
```

The visible UI remains completely stock.

## Why this hook is preferable

The hook is semantic rather than input-device specific.

It executes only after the stock frontend has already resolved the user's action as "open User Games." That means the implementation does not care which physical controller/input mapping produced the confirm event.

This is especially valuable because earlier Mapper archaeology proved that several inferred standalone raw-button identities were unsafe to assume.

## First runtime writer proof should remain staged

Test02 already proves stable catalog append on hardware.

Test03 already proves generated Zxx packaging on hardware.

The next unknown is not the catalog format or wrapper format. It is **device-side mutation of canonical built-in catalog files**.

Do not combine that first proof with general directory comparison logic.

Recommended Test04 architecture:

```text
User confirms User Games
        |
        v
hook row-0 dispatcher
        |
        v
detect a known staged refresh payload
        |
        v
device itself writes/replaces one synchronized catalog triplet
        |
        v
invalidate affected cached count
        |
        v
continue to stock User Games path
```

A successful Test04 proves:

- the stock UI hook is safe;
- canonical Resources files can be updated from the device runtime;
- filesystem sync/reopen behavior works;
- count invalidation works;
- existing Favorite/index references survive the on-device mutation.

After that proof, replace the staged source with the already-recovered native directory enumeration/stable-merge logic.

## Why not jump directly to the full scanner

A full first candidate would simultaneously introduce:

- directory enumeration;
- catalog parsing;
- filename comparison;
- fallback metadata generation;
- three-file serialization;
- recovery handling;
- UI trigger integration.

If it failed, the fault domain would be unnecessarily large.

The project has consistently made faster progress when each hardware test isolates one architectural question.
