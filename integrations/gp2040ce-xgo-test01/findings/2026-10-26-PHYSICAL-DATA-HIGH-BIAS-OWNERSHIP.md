# Universal controller reliability — XGO DATA released-HIGH electrical ownership

**Date:** 2026-10-26. **Branch:** `research-gp2040ce-xgo-integration`. This is the continuation after the owner explicitly corrected scope to **reliable controller transport in every game**. The checked specimen is the user-tested transparent GP2040-CE A and original stock XGO firmware; protected XGO GOLD host used on hardware is preserved. Status: XGO original opcode [BIN], exact RP2040 responder [SRC], Raspberry Pi SDK register definitions [UP], earlier passive hardware [HW], physical bias and faulty voltage threshold [OPEN]. **No firmware/cabling modifications or new hardware trial.**

## 1. A missing electrical contract, not a keymap

The controller currently transmits a pressed bit by driving the USB PHY's DP wire **LOW**, but transmits a released bit by disabling its output. A level of HIGH is **not generated by this action**. The console also forces that same physical DATA line LOW during LOAD and switches its own GPIO to input before reading the earliest bit. The physical circuit must therefore have a suitable HIGH-return bias somewhere else to make "released" unambiguous at its actual sample time.

The existing passive-P3 and GREEN-probe hardware observations — unexpected P2 game actions despite Pico TX output disabled or with additional probe loading — are consistent with possible DATA-line loading/bias/recovery sensitivity, but are **not proof** of an inadequate pull-up on Frankie V2 Jr. The owner's latest native-R released/held/released A-B-A result showed phantom P2 actions at about the same rate in every phase. This deprioritizes a four-instruction branch timing distinction without ruling out a bias fault persisting longer than both read paths, or a different serial bit.

## 2. Original XGO hardware scanner — host is LOW driver and early sampler [BIN]

The original user archive `/mnt/data/XGoAnalisis.zip` member `bios/bisrv.asd`, SHA256 `869e056d000337e1b10c834f0a93244c0abd99457c1c8374367f7dff20e43daf`, was read-only verified locally against **11 exact MIPS instructions** in the original scanner. Relevant L0 port MMIO (as confirmed by HC15xx family GPIO usage): 
- `0xB8800054`: L GPIO output value register; MIPS `0x8035D804` constructs base, `0x8035D818` writes the L0 output LOW.
- `0xB8800058`: L GPIO direction register; host sets bit0 for LOAD output at `0x8035D7CC`, later clears bit0 at `0x8035D864` so L0 becomes an INPUT.
- `0xB8800050`: L GPIO input register; original `0x8035D87C` constructs it, `0x8035D890` reads physical L0 immediately as external slot0/R0, before any CLOCK.
- The MIPS path calls interrupt helpers and the native-R branch between direction release and L0 read, but user hardware A-B-A did not show change in the phantom-action rate.

This scanner section toggles **output, direction, and input** MMIO. It does **NOT** demonstrate an explicit pull-up being enabled *inside this scan routine*. The existence/absence/strength of **board resistors or earlier GPIO pad initialization** is **OPEN**. Do not equate “not in the scan routine” with “no pull-up exists.” Previous P0 passive digital captures did in fact show DATA eventually returning HIGH, which establishes a later digital threshold crossing in those older conditions, not a guaranteed analog rise by the XGO's first sample.

Exact reproducible audit source: [`tests/verify_xgo_data_line_bias_contract.py`](../tests/verify_xgo_data_line_bias_contract.py) with `--stock-original XGoAnalisis.zip` for the SHA and MIPS checks, and a default source-only mode for CI. Local original MIPS eleven-opcode check PASSED.

## 3. Current GP2040-CE transparent A raw USB-PHY configuration [SRC/UP]

Protected driver [`candidates/offline-test44-transparent-controller/XGODriver.cpp`](../candidates/offline-test44-transparent-controller/XGODriver.cpp), immutable Git blob `cccb985a05baa8bb9078b6e336eb5f991c1a7a8f`:

```cpp
usb_hw->phy_direct = 0;
usb_hw->phy_direct_override =
    USB_USBPHY_DIRECT_OVERRIDE_DP_PULLUP_EN_OVERRIDE_EN_BITS |
    USB_USBPHY_DIRECT_OVERRIDE_DP_PULLDN_EN_OVERRIDE_EN_BITS |
    /* ... other override flags ... */;
inline bool data_level() { return (usb_hw->phy_direct & USB_USBPHY_DIRECT_RX_DP_BITS) != 0; }
inline void data_release() { clear_alias->phy_direct = USB_USBPHY_DIRECT_TX_DP_OE_BITS; }
inline void data_sink() { set_alias->phy_direct = USB_USBPHY_DIRECT_TX_DP_OE_BITS; }
```

With native DP = XGO DATA and DM = XGO CLOCK:
- `phy_direct=0` requests `DP_PULLUP_EN=0`, and the **explicit DP pull-up override-enable** makes that a controlled OFF request, not an unknown default.
- The explicit DP pull-down override-enable also requests OFF.
- `TX_DIFFMODE=0` single-ended output, `TX_DP=0`. Enabling only `TX_DP_OE` sinks DP LOW. Clearing OE releases DP to **Hi-Z**. There is **no active HIGH transmission**.
- `DM_PULLUP_OVERRIDE_EN` is **not enabled** in the protected A source, unlike the DP pull-up override. In the historical earlier native USB-PHY P3 trial, changing the DM pull-up override explicitly made the XGO freeze. That historical case happened on an ordinary native cable, not present Frankie; it is NOT an authorization to repeat it and it does not prove which line/pull resistor was responsible.

The RP2040 register definitions describe physical RX_DP/RX_DM input read bits, independently controllable TX output-enable and pull-enable override bits. These facts come from [Pico SDK RP2040 `USBPHY_DIRECT` definitions](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2040/hardware_regs/include/hardware/regs/usb.h) and RP2040 datasheet USB PHY section, not from assumed standard USB HID operation. The PCB connector is used by a proprietary active-LOW shift bus.

**The precise proven electrical-contract gap:** both the controller's released output and the XGO's post-LOAD input direction are not active HIGH drivers. Source confirms the **controller DP internal pull-up is forced OFF**. It does NOT determine whether the XGO GPIO internally pulls up DATA, whether the XGO PCB includes an external bias resistor, or whether the connected Frankie cable has leakage/extra capacitance. It likewise does NOT justify asserting the line literally floats at all times.

## 4. Symptoms this could explain — and symptoms it cannot uniquely explain

- If the DATA rise is slow or line is biased inadequately when XGO reads the first slot, it can decode a false LOW = pressed while GP2040 published physical mask is zero. This could produce an *idle phantom button* even when `emit_frame()` reports completed serial transmission and no CLOCK errors.
- If DATA return is delayed into the following CLOCKs, more than one bit can be corrupted. A source-extracted simulation previously established that the controller may also miss the first CLOCK after its `wait_data(true,18us)` release gate, shifting later held bits and causing an eventual S12 timeout.
- The old observed spurious PAUSE and intermittent held-button substitution need not be the same cause as the present P2 phantom actions. Later-slot electrical errors, clock observation loss, Core0 OLED blocking and active input state remain separate candidates. A single "R0 filter" is not acceptable because every genuine button must remain functional.

**Important negative control:** User hardware native-R A-B-A showed no rate difference. The specific small first-read path length is NOT an effective lever for this observed symptom; do not repeat it or patch GOLD timing based on it.

## 5. Actionable engineering decision, not another arbitrary candidate

**Do not enable the RP2040's DP internal USB pull-up as a blind firmware test.** Although its register is available, that pull-up could source current into XGO's active LOW LOAD driver and its electrical voltage/current budget is not established. The previous DM pull-up experiment froze XGO, and the working Frankie connector has nonstandard bridged physical pads. Also do not actively drive HIGH, add an inline resistor arbitrarily, change the 18us wait, remap first-button or patch the host GOLD BIOS.

Before any *transport-only* fix: establish DATA HIGH-bias source and compatible voltage, then confirm DATA rise relative to console's input-sampling timing with measurement that does not itself create phantom actions. Candidate remedy classes, contingent on those facts, are **proper DATA bias/pull-up** or **separately isolated true open-drain/level-conditioning circuitry**; both require board-specific electrical qualification, not blind parts. The existing low-risk separate Core0 paged-OLED trial already compiled to address **missed short taps**, but is unflashed and **does not fix idle ghost**. These are two genuinely different reliability workstreams; do not let display remediation disguise a DATA fault.
